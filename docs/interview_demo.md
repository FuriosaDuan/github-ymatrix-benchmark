# Benchmark V3 面试展示材料

## 30 秒项目介绍

这是一个面向 YMatrix 与 MySQL 的 SQL Benchmark 工具，用于 PoC、性能验证和竞品对比。工具用固定 seed 生成四张简化 TPC-H 风格表，使用 psql/mysql 命令行客户端执行同一组 SQL，区分 warmup 和正式轮次，记录端到端耗时，并生成 CSV、Markdown、环境信息和日志。正式 benchmark 前会校验两套数据库的行数和查询结果一致性，保证结果可复现、可解释。

## 2 分钟技术说明

- Windows 负责代码、mock unittest、compileall 和 Git；Linux 负责真实数据库执行。
- 通过 subprocess 调用 psql 和 mysql，不安装第三方 Python 数据库驱动。
- 密码只通过子进程环境变量传递，不进入命令行、日志或报告。
- 两套数据库各自使用 session_sql 与查询拼成同一个客户端进程，保证会话参数生效。
- warmup 结果不进入正式明细；正式轮次使用 time.monotonic 计时。
- p95 使用 nearest-rank：ceil(0.95 * n)。
- 首次查询结果被规范化为字符串/Decimal，用于两套数据库业务结果一致性校验。
- 报告包含逐查询统计、数据库对比、Top 慢 SQL、失败分类、环境和限制。

## 面试可能追问

### 为什么不用 Python 数据库驱动？

目标 Linux 已确认有 psql 和 mysql 客户端，命令行方式无需安装第三方包，部署面更小，也能真实记录客户端启动和连接建立开销。后续可以增加驱动适配，但必须明确计时口径。

### 为什么采用命令行客户端？

它与现场运维方式一致，能直接复用现有认证和客户端版本，并将每次查询隔离为可审计的 subprocess。

### 为什么使用 monotonic？

墙上时钟可能被 NTP 或人工调整，monotonic 只向前走，适合测量耗时。ISO 8601 时间戳只负责记录可读的开始和结束时刻。

### 为什么需要 warmup？

第一次执行可能包含客户端启动、连接建立、缓存和执行计划初始化成本。warmup 可以降低冷启动对正式轮次统计的影响，但报告仍说明端到端口径。

### p95 如何计算？

先排序成功轮次耗时，取 rank=ceil(0.95*n) 的 nearest-rank 值；失败轮次不进入耗时统计，但进入成功率和失败分类。

### 为什么当前测试不属于标准 TPC-H？

当前只有四张简化表和三条自定义查询，数据规模、数据分布和查询集合都不是 TPC-H 标准规范。

### 怎样扩展到完整 TPC-H？

增加标准八表 schema、标准数据生成器、22 条 SQL、规模因子配置和标准结果校验；同时记录标准版本和执行协议。

### 怎样扩展 concurrency？

将单轮执行封装为任务，使用标准库线程或进程池，并记录并发度、连接数、调度开销和每个 worker 的结果；当前 MVP 明确只支持 1。

### 怎样扩展到 TPC-C？

增加 TPC-C 事务模型和混合事务生成器，把查询执行接口扩展为事务工作负载接口，并记录吞吐、延迟和事务成功率。

### 如何保证两套数据库对比公平？

使用同一份 CSV、同一数据规模、同一轮数、同一 warmup 策略和同一客户端计时口径；SQL 只做语法适配，先校验结果一致，再比较性能。

### 当前测试结果有哪些限制？

单节点、小规模、低并发，短 SQL 会受客户端启动和连接建立影响；结果只适用于报告记录的硬件、版本、参数和数据规模。

### 如果数据量扩大到 10GB，需要修改哪些部分？

数据生成和加载需要流式处理、可配置批大小、并行装载和更严格的磁盘/网络监控；benchmark 需要更长轮次、稳定性复测和 EXPLAIN/EXPLAIN ANALYZE 诊断。
